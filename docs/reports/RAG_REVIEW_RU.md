**Проблемы работы, которые нужно устранить до сравнения моделей**

1. **Индекс не соответствует текущей папке данных.** Индекса `faiss_indexes/Банкинг` нет. В `finance` всего 64 вектора размерности 3 072; в `legal` один тестовый фрагмент про вымышленную компанию. Старый `faiss_index` содержит 65 векторов и текущей цепочкой не используется. Сохранённые пути ведут в `D:\RAG\data\...`, а не в текущую папку. При выборе «Банкинг» код должен создать новый индекс; старые индексы нельзя считать индексом всех 47 PDF.
2. **Добавленные документы не обновляют готовый индекс.** Проверяется существование папки индекса, после чего загрузка исходных документов пропускается. `/clearcache` очищает оперативную память, но не обновляет индекс на диске. Нужен manifest с хешами файлов и настройками embedding/chunking, инкрементальная обработка изменений и атомарная замена готового индекса.
3. **Поиск не учитывает историю.** Генератор видит диалог, retriever получает только последнее сообщение. Вопрос «А в предыдущем квартале?» может найти неправильный контекст. Передавать в поиск сохранённые сущность и период; отдельное переформулирование моделью делать лишь при реальной неоднозначности.
4. **Модель не получает метаданные источника.** `format_docs()` склеивает только текст. Нужно передавать короткую метку документа, страницу, период и дату; ответ должен ссылаться на конкретные фрагменты. Кнопка скачивания найденного PDF не доказывает, что он подтверждает каждое число в ответе.
5. **Всегда выбираются ближайшие фрагменты без проверки релевантности.** Добавить порог, откалиброванный на вопросах по этому корпусу, и отказ при нехватке источников. Для сводок обеспечить разнообразие документов. Не переносить один числовой порог между embedding-моделями без проверки.
6. **Синхронные операции блокируют Telegram event loop.** `.invoke()` и первичная индексация вызываются внутри async-обработчиков. Использовать асинхронный вызов/worker и готовить индекс отдельно. Даже одному пользователю это влияет на отзывчивость меню.
7. **Сбой классификатора скрывает уже полученный ответ.** Второй вызов находится в общем try. Из-за его ошибки оплаченный текст не будет показан, что провоцирует повторные запросы.
8. **Ненадёжная визуализация чисел.** Второй LLM извлекает данные из сгенерированного ответа, а не проверенной таблицы; единицы и периоды не валидируются. Для графика нужны структурированные данные и локальный рендер. При выборе графика текстовое объяснение сейчас не отправляется.
9. **Поставленная копия требует настройки запуска.** `API_TOKEN` пуст; matplotlib импортируется, но отсутствует в requirements.txt. Кнопка «Справка» не имеет отдельного обработчика и после выбора темы попадёт в RAG. HTML ответа не экранируется, длинные сообщения не разбиваются.
10. **Streamlit разделяет историю по теме, а не по пользователю.** `session_{selected_topic}` и глобальный `store.clear()` будут смешивать/очищать сессии при нескольких пользователях. При заявленном одном пользователе приоритет ниже.

**Локальные embeddings.** Для экономного поиска кандидат — `intfloat/multilingual-e5-small`: 384 измерения, мультиязычная модель, максимум 512 токенов; обязательны префиксы `query:` и `passage:` даже для русского текста. Для 2 GB рассмотреть заранее подготовленный ONNX INT8 и небольшой batch, замерив пиковую память. Альтернатива с минимальными требованиями — SQLite FTS/BM25 с нормализацией русских слов, словарём названий банков и фильтрами дат; его полноту поиска нужно сравнить с dense retrieval. Источники: [карточка e5-small](https://huggingface.co/intfloat/multilingual-e5-small), [ONNX и ускорение inference](https://www.sbert.net/docs/sentence_transformer/usage/efficiency.html).

При смене embedding-модели индекс нужно полностью перестроить: одинаковая размерность не делает пространства совместимыми. Хранить название/версию модели, размерность, нормализацию и правила префиксов в manifest. Для одинакового числа float32-векторов 384 измерения занимают в восемь раз меньше памяти, чем 3 072; это не означает восьмикратное сокращение всей памяти приложения. BGE-M3 с длинным контекстом можно сравнить на домашнем ПК, но для минимального VPS он не первый выбор: [карточка BGE-M3](https://huggingface.co/BAAI/bge-m3).

**Полностью локальная генерация.** Начальная конфигурация для проверки — Qwen3 8B Q4 через Ollama, короткий контекст и отключённое thinking для извлечения фактов. Один файл модели имеет размер 5,2 GB, поэтому VPS с 2 GB не обеспечивает нормального размещения такой модели вместе с рабочим контекстом. Практический ориентир для домашнего ПК — 16 GB RAM или больше; видеокарта ускорит генерацию. Это рекомендация для пилота, не измеренный минимум: реальная память и скорость зависят от контекста и оборудования. Модели 0,6–1,7B легче, но их качество финансового синтеза здесь не проверено, замену Gemini ими не рекомендую без оценки. Источник: [Qwen3 8B Q4](https://ollama.com/library/qwen3:8b).

**Расчёт стоимости, а не фактический счёт**

30 дней, 300–1 500 вопросов в месяц. Стандартные тарифы за миллион токенов: Flash 2.5 — $0,30 вход / $2,50 выход; Flash-Lite 2.5 — $0,10 / $0,40; Gemini Embedding 001 — $0,15 за вход. Источник тарифов и условий бесплатного уровня: [Google pricing](https://ai.google.dev/gemini-api/docs/pricing). На бесплатном уровне данные могут использоваться для улучшения продуктов; для внутренних документов это нужно учитывать при выборе сервиса.

Формула: `число вопросов × (входные токены × цена входа + выходные токены × цена выхода) / 1 000 000`.

| Сценарий | Токены на вопрос | 10 вопросов/день | 50 вопросов/день |
|---|---|---:|---:|
| Иллюстрация текущей двухшаговой схемы Flash | Суммарно 2 200 вход / 700 выход | $0,72 | $3,62 |
| Один вызов Flash | 2 000 вход / 600 выход | $0,63 | $3,15 |
| Один вызов Flash-Lite | 2 000 вход / 600 выход | $0,13 | $0,66 |

Для первой строки условно приняты 1 500 вход / 600 выход для ответа и 700 вход / 100 выход для intent. Это не измерение проекта. Накопленная история и thinking в эти сценарии не включены; текущая реализация может расходовать существенно больше. Расходы на VPS, изображения, индексацию, повторные запросы и налоги также не включены.

Отдельный ориентир для embedding вопросов: при 100 токенах на вопрос и 1 500 вопросах — около $0,0225 в месяц. Поэтому переход на локальные embeddings при этой нагрузке нужен прежде всего для независимости и квот, а не для большой денежной экономии. Объём корпуса измерен в символах, не в токенах Gemini: точную цену первоначальной индексации без tokenizer/countTokens и фактической нарезки не утверждаю.

**Предлагаемый порядок доработки**

1. Добавить usage-метрики для каждой стадии: модель, вход/выход/thinking/cache, длительность, статус, повторный вызов. Для обычного ответа целевой путь — один вызов генерации, для выдачи источника/справки — ноль.
2. Убрать intent-вызов по умолчанию; ограничить историю и выход; добавить отдельные кнопки графика/сводки; проверять пользовательский ID для личного бота, чтобы чужие запросы не расходовали квоту.
3. Создать корректный индекс «Банкинг», manifest и обновление изменённых файлов; передавать даты и ссылки на страницы в контекст.
4. Очистить колонтитулы и служебные повторы. Обрабатывать таблицы с сохранением заголовков; для обзоров готовить карточки документов один раз при изменении источника и проверять их по оригиналу.
5. Сравнить Flash, Flash-Lite и бесплатную альтернативу на 30–50 реальных вопросах: точные числа/единицы, факт против прогноза, сравнение двух периодов, продолжение диалога, обзор нескольких источников, вопрос без ответа в базе. Измерять точность, наличие подтверждающей страницы, полноту поиска, токены и задержку. Не обещать одинаковое качество моделей без этого сравнения.
6. Разместить лёгкий runtime на VPS: один процесс бота, один общий индекс, SQLite, очередь запросов. Подготовку PDF и тяжёлую индексацию выполнять на ПК и переносить готовый индекс вместе с согласованной версией текстов и метаданных. Streamlit запускать только при необходимости; графики строить по запросу. Для e5/ONNX отдельно измерить RSS и запас до лимита 2 GB.

На этом этапе не требуется миграция в отдельную векторную СУБД, дообучение модели или сложная агентная система. Наибольшую пользу дадут управляемый одинарный LLM-вызов, корректные данные и проверяемые источники.
