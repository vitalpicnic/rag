# Общий RAG runtime

Этап 8 добавляет `RagRuntime`, `RuntimeQueryHandler`, ограниченный кэш и блокировку
владельца модели. Это внутрипроцессный backend; перевод CLI, Telegram и Streamlit
на общий HTTP API относится к этапу 9. Старые интерфейсы пока работают через legacy
engine и не должны запускаться параллельно с новым runtime на production-сервере.

## Выполнение запросов

`rag.engine.create_runtime(root, settings, token_counter, privacy_store=...)` создаёт
одну пару embedding/generation на весь runtime. Для разработки и тестов разрешена
явная доверенная `model_factory`; пользовательский запрос её не выбирает.
Runtime требует local embeddings, точный счётчик соответствующей модели и политику
для внешнего провайдера. LOCAL с Ollama не требует разрешения на внешнюю генерацию.
Существующая проверка production-токенизатора в фабрике Ollama не отключена.

```python
# settings, token_counter и policy_store создаются доверенной конфигурацией сервера.
from rag.engine import create_runtime

runtime = create_runtime(root, settings, token_counter, privacy_store=policy_store)
try:
    result = runtime.query({
        "principal": "cli:user-1",
        "session": "conversation-1",
        "topic": "default",
        "mode": "expert",
        "question": "Как изменились активы банка?",
    })
finally:
    runtime.drain()
```

- Один worker выполняет запросы последовательно. Очередь содержит не больше 8
  ожидающих запросов; по умолчанию ожидание результата и срок очереди — 60 секунд.
  `RuntimeBusy` означает отказ в приёме/истёкшую очередь. `TimeoutError` означает
  истёкшее ожидание клиента; это не подтверждение прекращения вычисления.
- `submit()` возвращает Future. Запущенное вычисление удерживает слот до своего
  завершения, даже после отмены клиента. Ожидающее отменённое задание пропускается.
  `rag.bot_support.query_runtime()` использует эту очередь без второго worker.
- Зависшее выполнение, включая проверку индекса, по умолчанию через 180 секунд
  вызывает `os._exit(70)`. Новый worker внутри повреждённого процесса не создаётся.
  Перезапуск процесса должен выполнять supervisor из этапа развёртывания.
- История разделена ключом `(principal, session, topic, mode)`. Сохраняются до 8
  полных пар и 64 KiB текста на сессию; LRU содержит до 256 сессий. Точный лимит
  отправляемой истории дополнительно задаёт packing. Ошибочный запрос не сохраняет
  новую историю. Внешняя история без source provenance по-прежнему запрещена.
- `principal` здесь считается уже аутентифицированным адаптером. Проверка
  service secret и авторизация пользователя относятся к будущему HTTP API.

## Индексы и память

Кэш ограничен 512 MiB **оценённой** памяти FAISS/docstore. До загрузки проверяются
указатель, размеры файлов и manifest с ограничением 100 000 chunks. Резерв:
`4 × index.faiss bytes + 24 × chunks.jsonl bytes + 8192 × chunks + 2 MiB`.
Это консервативная эвристика с запасом на временные копии и перепроверку, а не
измерение RSS. Фактический предел памяти должен дополнительно обеспечивать cgroup;
проверка RSS/OOM на Linux VPS ещё не выполнена.

Индекс, не помещающийся в резерв, отклоняется до FAISS load. При нехватке места
вытесняются наиболее давно использованные незакреплённые записи. Закреплённый
запросом индекс не вытесняется. Вместе с записью освобождается её verifier — скрытый
неограниченный кэш snapshots за LRU не остаётся. Native allocator может удерживать
освобождённую память; перед индексацией на минимальном VPS предпочтительно завершить
процесс runtime после drain.

Worker обслуживает проверки snapshots между запросами и примерно раз в секунду
при простое. Сохраняются интервалы watcher/full verify/expiry 30/3600/7200 секунд;
во время длинного запроса они могут задерживаться. Перед каждым count/generation
и выдачей результата повторно проверяется lease указателя и срок действия snapshot.
Смена версии в ходе генерации отбрасывает ответ. Изменение файлов с прежним
указателем обнаруживается watcher/полной проверкой, а не немедленно на каждом вызове.

`readiness()` показывает admission, active и queued. `readiness(topic)` также
проверяет уже загруженную тему, не загружая её. Холодная тема ещё не ready, первый
запрос выполняет её проверку/загрузку. Это не полноценный health probe доступности LLM.

## Maintenance и владельцы

Runtime захватывает kernel lock `ROOT/.model-owner.lock` **до** создания модели.
`scripts.index_admin` использует тот же lock перед build/verify/activate/rollback,
включая создание embedding-модели. `--maintenance` остаётся обязательным для
мутаций. Отдельный процесс индексатора отклоняется, пока runtime удерживает lock.

`drain()` закрывает приём, отменяет очередь, ожидает реальное завершение worker,
очищает кэш и историю, удаляет ссылку на модель, запускает GC и освобождает lock.
После drain объект не возобновляется: создайте новый runtime. Если worker не
завершился, lock не освобождается. Файл lock не удаляется вручную; ОС освобождает
блокировку при завершении процесса. Все cooperating процессы обязаны использовать
один и тот же root. Legacy-команды и прямые вызовы библиотечных функций блокировку
автоматически не получают; их обслуживание требует остановленного serving.

## Проверки и границы готовности

17 тестов `tests/test_runtime.py` проверяют очередь, отмену, изоляцию сессий,
однократную фабрику модели, LRU/pinning, отказ до allocation, административный lock,
отзыв snapshot и полный путь FAISS → packing → подставная LLM. Межпроцессная
блокировка и аварийное завершение проверены настоящими дочерними процессами Windows.

```bash
python -m unittest discover -s tests -p test_runtime.py -q
```

Не проверены: Linux flock/cgroup, лимиты и latency на VPS, реальная Ollama/Gemini,
соответствие локального tokenizer конкретному digest модели. Рабочий backend
счётчика и перенос интерфейсов на HTTP API остаются обязательными до production.
