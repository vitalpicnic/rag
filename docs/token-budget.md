# Бюджет полного запроса

`rag/token_budget.py` собирает окончательные сообщения перед генерацией. Подключение:
`build_history_chain(..., token_counter=TokenCounter(contract, count_tokens))`.
Счётчик и контракт задаёт код провайдера, не HTTP-запрос пользователя.
Без счётчика production-цепочка не создаётся; прежнее поведение development сохранено.

## Правила упаковки

- Вход ограничен меньшим из 16 384 токенов и лимита модели. При общем окне из него
  заранее вычитаются резервы ответа и thinking.
- Резерв ответа: text 600, overview/executive 1800, expert 3000. Он уменьшается,
  если лимит провайдера после резерва thinking меньше. В этой версии контракта
  thinking входит в output limit; клиент получает их суммарный `max_output_tokens`.
- Safety margin: максимум 256 и округлённых вверх 5% эффективного входного лимита.
- Сначала проверяется обязательный prompt с текущим вопросом. Вопрос не обрезается.
- История содержит только полные пары user/assistant, не больше 800 токенов
  выбранного счётчика, включая его framing. Старейшие пары удаляются первыми.
- При нехватке общего бюджета история сокращается раньше evidence. Источники
  сохраняют официальный приоритет и альтернативную позицию при вместимости.
  Фрагмент с заголовком цитирования добавляется целиком или пропускается.
- Финальный набор сообщений повторно подсчитывается и передаётся модели без
  повторного построения prompt. Возвращаются только реально использованные источники.
- Неизвестный контракт, ошибка счётчика, слишком большой вопрос или отсутствие
  помещающегося evidence дают `BudgetDenied` до генерации.

Счётчик получает полный список сообщений, включая инструкции роли, метаданные
источников и citation headers. Он обязан учитывать реальный chat template/framing
модели. Поэтому сумма отдельных оценок и UTF-8 bytes/4 не используются как точный
финальный подсчёт. Существующий `BoundedHistory` остаётся legacy-хранилищем;
новый runtime должен передавать упаковщику исходные целые пары истории.

## Контракт провайдера

`TokenContract` содержит `model`, `counter_id`, `input_limit`, `output_limit`,
`context_limit`, `thinking_tokens`, `external`, `provider`, `endpoint`.
`context_limit=None` означает документированно независимые входной и выходной лимиты,
а не неизвестный размер окна. `thinking_tokens=0` допустим при отключённом thinking.
Имя модели контракта должно совпадать с `model_name` цепочки.

`TokenCounter(contract, count_tokens)` — интерфейс интеграции. Callable возвращает
целое неотрицательное число токенов для полных сообщений. Его точность нельзя
установить по одному имени `counter_id`: доверенная фабрика провайдера должна
проверить соответствие модели, tokenizer/chat template, digest и настроек генерации.
Смена tokenizer или thinking policy требует другого проверенного контракта.

Для внешнего счётчика обязательны совпадающие provider/endpoint и privacy lease,
покрывающий все передаваемые источники. Политика проверяется до и после каждого
подсчёта. История без provenance по-прежнему запрещена во внешних запросах.
Генерация использует тот же lease, а не новое разрешение после упаковки.

В метриках `stage=token_budget` сохраняются preflight/actual input tokens, разница,
лимит, margin и резервы. Тексты, prompts и evidence в эту запись не входят.
Фактический usage служит аудитом и не заменяет предварительную проверку.

## Проверки и оставшаяся интеграция

17 адресных тестов проверяют четыре режима, Unicode/таблицы, целостность evidence,
полные пары истории, разные счётчики, thinking/context reserve, отказ до генерации,
privacy и совпадение подсчитанного prompt с переданным модели.

```bash
python -m unittest discover -s tests -p test_token_budget.py -q
```

Тестовые счётчики детерминированы и намеренно отличаются между собой; это не
production-токенизаторы Gemini/Ollama. Рабочие backend-счётчики ещё не подключены:
для Ollama нужны установленная модель и проверенное соответствие её digest
локальному tokenizer/chat template; для Gemini — API countTokens после privacy gate.
Неизвестный backend не получает приблизительный fallback. Production-запрет
в `create_generation` для Ollama сохранён. Реальная LLM и Linux VPS не проверялись.

Следующий этап — общий runtime, очередь и владение моделью. Реальные счётчики и
live-приёмка остаются обязательными условиями production. Сравнение качества A/B
не выполнено: изменение packing требует отдельного контрольного прогона и затем
одинакового packing в обеих ветках эксперимента embeddings.
